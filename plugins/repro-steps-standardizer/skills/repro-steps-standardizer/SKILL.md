# 复现步骤整理

## 何时使用

- bug 描述只有一句「点了保存就报错」。
- 要与开发交接，需要一份对方能照着复现的单子。
- 要把录屏或聊天记录转成结构化的缺陷单。

## 步骤

### 1. 补齐五个必备要素

| 要素 | 不合格示例 | 合格示例 |
| --- | --- | --- |
| 环境 | 「最新版」 | Android 14 / 应用 v3.2.1 / 账号 A |
| 数据 | 「有个订单」 | 订单 ID 12345，状态「已支付」，2 个子订单 |
| 步骤 | 「随便点点」 | 1) 进订单列表 2) 筛「已支付」 3) 点第 1 条 4) 点「申请退款」 |
| 期望 | 「应该正常」 | 弹出确认框，退款单状态为「处理中」 |
| 实际 | 「报错了」 | 弹「网络异常」，订单状态仍为「已支付」，重试仍失败 |

### 2. 最小化

逐步删除步骤，直到再删就不能复现。常见可删项：无关的登录方式、无关的筛选条件、无关的设备旋转。每删一步记录「删除后仍复现」以便背书。

### 3. 定位复现率

`必现` / `偶发（约 N/M 次）` / `仅首次` / `仅在弱网` / `仅新账号`。偶发要给出尝试次数与成功次数，不要写「有时」。

### 4. 证据

- 截图：关键状态 + 错误提示完整可见。
- 日志：带时间戳，前后各 5 行，脱敏后附上。
- 录屏：从操作起点开始，不剪辑中间步骤。
- 网络：失败请求的状态码、请求 ID、响应体（脱敏）。

### 5. 判重与关联

在已有缺陷单里按「页面 + 操作 + 错误特征」搜索，命中则关联而非新建；标注是否阻塞、影响用户范围。

### 6. 复现单输出

```markdown
## <模块> <一句话现象>

**严重度**：S1 阻断 / S2 严重 / S3 一般 / S4 轻微
**复现率**：必现（5/5）

### 环境
- 平台/版本：<...>
- 账号/租户：<脱敏>
- 网络：<Wi-Fi/4G/弱网模拟>
- 数据前置：<订单/文档/权限>

### 复现步骤
1. ...
2. ...
3. ...

### 期望结果
### 实际结果
### 证据
- 截图：<...>
- 日志：
```text
<脱敏后的 10 行>
```
- 请求：`POST /api/...` → 500，request-id: ...

### 最小化尝试
| 删掉的步骤 | 仍复现 |
| --- | --- |

### 附加信息
- 首次发现时间 / 最近一次正常版本
- 是否与已知缺陷重复：<#ID>
```

## 判定规则

- 缺「环境」「数据」「期望」「实际」任一项 → 打回，不算合格复现单。
- 步骤出现「然后」「等等」「类似」这类模糊词 → 必须展开。
- 未给复现率 → 标为「未验证」，不能当作必现。
- 日志未脱敏 → 阻断提交，先要求脱敏。
- 期望结果不可判定（「应该更好用」）→ 重写为可观察的状态。

## 纪律

- 不替用户编造环境与数据；缺失项写 `<待补充>`。
- 不改写用户提供的错误原文，只做脱敏。
- 不合并多个现象到一张单，一次一个缺陷。
- 复现步骤必须逐步可执行，不写「按正常流程操作」。
