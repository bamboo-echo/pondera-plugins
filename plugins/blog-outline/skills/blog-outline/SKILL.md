# 技术博客大纲

## 何时使用

- 用户给出主题、零散笔记、一次踩坑经历，想要成文结构。
- 文章初稿「什么都讲了但没重点」，需要收敛论点。
- 需要判断素材是否足够支撑一篇长文。

不负责直接写完全文，也不做 SEO 关键词堆砌。

## 执行步骤

1. **确定读者**：写出「读者是谁、已经会什么、读完要能做什么」。三者缺一不可。
2. **锁定唯一论点**：一句话，含「在什么条件下、做什么、能得到什么」。一篇文章只允许一个主论点。
3. **梳理证据链**：每个分论点至少配一个证据类型——可运行代码、实测数据、复现步骤、对照实验、真实事故。没有证据的分论点删掉或降级为「待验证」。
4. **预设反例**：主动写出「这个方案在什么情况下不成立」，避免文章一边倒。
5. **编排结构**：按「问题 → 直觉方案为何不够 → 本文方案 → 证据 → 边界 → 结论」组织，每节标注篇幅（短/中/长）。
6. **给出标题候选**：3 个，分别对应「问题导向」「结果导向」「反常识」，不用夸张词。
7. **列出待补素材**：还缺哪些数据、截图、复现环境，按重要性排序。

## 判定规则

- 论点无法用一句话说清 → 文章会散，回到第 2 步。
- 分论点无证据 → 删除，不要用「一般来说」补位。
- 例子超过 2 个同类型 → 合并，避免重复论证。
- 涉及性能/成本数字 → 必须标明测试环境，否则写成「定性」。
- 读者画像与选题不匹配（如面向新手却讨论内核调度）→ 先改读者，再改大纲。

## 输出格式

```markdown
## 大纲：<工作标题>

**读者**：<是谁 / 已知 / 读后能做>
**主论点**：<一句话>
**预计篇幅**：<字数量级>

### 结构
1. **问题**（短）：<...>
2. **直觉方案为何不够**（短）：<...>
3. **本文方案**（中）：<...>
   - 证据：<代码 / 数据 / 复现步骤>
4. **实测与对照**（中）：<...>
5. **边界与反例**（短）：<...>
6. **结论**（短）：<...>

### 标题候选
1. <问题导向>
2. <结果导向>
3. <反常识>

### 待补素材
- [ ] <...>（优先级：高/中/低）
```

## 纪律

- 不写正文，只产大纲；用户确认结构后再展开。
- 不夸大结论，不在标题里使用「彻底」「颠覆」。
- 素材不足时明说「只能写成短文」，不要注水。
