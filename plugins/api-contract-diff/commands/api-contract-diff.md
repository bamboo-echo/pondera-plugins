---
description: 对比新旧 API 契约，输出破坏性/兼容性变更清单与过渡方案
argument-hint: [旧契约路径或版本] [新契约路径或版本]
---

对下面两个 API 契约做结构化差异分析。

- 旧契约：`$1`
- 新契约：`$2`
- 若 `$1`/`$2` 为空，按 `$ARGUMENTS` 顺序解析；仍为空则分别取 `git show <最近 tag>:<spec 路径>` 与工作区 `<spec 路径>`。
- 契约文件可能是 OpenAPI 3.x、Swagger 2.0、JSON Schema，或一份手写路由表。先说明你判断的类型，再开始比对。

**分析步骤**

1. 解析两份契约的端点集合、方法、路径参数、请求体字段、响应字段、错误码、鉴权方式。
2. 逐维度比对，每处差异标注方向（新增 / 删除 / 改名 / 类型变化 / 约束收紧或放宽 / 默认值变化 / 必填性变化）。
3. 按「客户端会不会因此报错」判定破坏性等级：
   - 删除字段、删除端点、收紧必填、缩小枚举、改类型、改语义 → 破坏性
   - 新增必填请求字段、改错误码含义 → 破坏性
   - 新增可选字段、新增端点、放宽约束、新增错误码 → 兼容
4. 对每处破坏性变更给出过渡方案：别名双写、字段并存期、deprecation 标记、版本化路径、兼容默认值。
5. 给出验证方式：契约测试、`oasdiff`、消费者侧回归清单；无法自动验证时明确写「需人工验证」。

**输出格式**

```markdown
## 契约差异：<旧版本> → <新版本>

**契约类型**：<OpenAPI 3.1 / Swagger 2.0 / ...>
**比对范围**：<端点数、schema 数>

### 破坏性变更
| # | 端点 | 变更 | 影响 | 过渡方案 |

### 兼容性变更
| # | 端点 | 变更 | 说明 |

### 契约质量问题（与本次差异无关但会影响判断）
- ...

### 结论
<能否直接上线；需要哪个版本并行期>
```

**纪律**

- 只报告契约文件里能证实的内容；字段缺失按「契约未声明」处理，不要推测实现行为。
- 不修改契约文件，先给结论；用户确认后再改。
- 同一变更不要拆成多条凑数；影响相同则合并。
