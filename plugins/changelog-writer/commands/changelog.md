---
description: 根据 git 提交记录生成结构化 CHANGELOG（按类型分组、标注破坏性变更）
argument-hint: [版本号或提交范围，例如 v1.2.0..HEAD，留空则用最近一次 tag 到 HEAD]
---

请为当前仓库生成一段 CHANGELOG 条目。

**范围**：`$ARGUMENTS`
如果上面为空，先执行 `git describe --tags --abbrev=0` 找到最近 tag，范围取 `<tag>..HEAD`；没有 tag 时取最近 50 个提交。

**执行步骤**

1. 用只读命令读取提交，不要修改仓库：
   ```bash
   git log --no-merges --pretty=format:'%h%x09%s' <范围>
   ```
2. 逐条按提交信息前缀归类：`feat` / `fix` / `perf` / `refactor` / `docs` / `build` / `ci` / `test` / `chore`。
   没有规范前缀的提交，按实际改动归入最接近的一类；无法判断就放进「其他」。
3. 识别破坏性变更：提交正文含 `BREAKING CHANGE:`，或标题带 `!`（如 `feat(api)!:`）。
   必须写清「旧行为 → 新行为 → 迁移方式」，迁移方式只能来自提交正文，不能自行推测。
4. 按下面的模板输出，版本号取 `$ARGUMENTS` 中的版本；没有版本号时用 `Unreleased`。

**输出模板**

```markdown
## [<版本或 Unreleased>] - <YYYY-MM-DD>

### 新功能
- <一句话说明，带提交短 sha>（<提交数> 个提交）

### 修复
- ...

### 性能
- ...

### 重构 / 构建 / 文档 / 测试
- ...

### 破坏性变更
- **<变更点>**：旧行为 → 新行为。迁移：<步骤>

### 其他
- ...
```

**纪律**

- 只写提交里真实存在的内容；不得编造功能、作者或 issue 编号。
- 合并提交、版本号提升类提交（`chore(release)`）不单独列出，除非其中含破坏性变更。
- 同一主题的多个提交合并为一条，并在末尾标注提交数量。
- 空分类直接省略该小节，不要留「无」。
- 除非用户明确要求，不要写入 `CHANGELOG.md` 文件，先在对话中给出结果。
