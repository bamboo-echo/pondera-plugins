分析 `$1` 的性能问题，执行计划来自 `$2`（为空则先给出取计划的方法，不臆造计划）。

**执行步骤**

1. 先判定数据库：PostgreSQL（`EXPLAIN (ANALYZE, BUFFERS)`）、MySQL 8（`EXPLAIN ANALYZE` / `EXPLAIN FORMAT=TREE`）、SQLite（`EXPLAIN QUERY PLAN`）。给出对应取计划命令，不要混用。
2. 通读计划，标记每类问题：
   - 全表扫描出现在过滤后行数很少的表上。
   - Nested Loop 的内表被反复扫描且无索引。
   - 估算行数与实际行数差异 > 10 倍 → 统计信息过期或谓词不可估算。
   - Sort/Hash 溢出到磁盘（`Sort Method: external merge`、`Disk:`）。
   - 隐式类型转换（`col::text = '...'`、字符串列与数字比较）导致索引失效。
   - 函数包裹索引列（`WHERE lower(name) = ...` 且无表达式索引）。
3. 逐条给出修复：新建索引（含列顺序与是否 INCLUDE）、改写谓词（可索引形式）、拆分查询、预聚合、限制返回列。
4. 给出验证方式：改写前后 `EXPLAIN ANALYZE` 的耗时与扫描行数对比；索引上线后观察写放大。
5. 标注风险：新索引会增加写成本；`CONCURRENTLY` 建索引避免锁表。

**输出格式**

```markdown
## SQL 计划审读

**数据库**：<...>　**取计划命令**：<...>

### 关键节点
| 节点 | 表 | 估算行数 | 实际行数 | 耗时 | 问题 |

### 问题与修复
| # | 问题 | 证据（计划片段） | 修复 | 预期收益 | 风险 |

### 建议 SQL
```sql
<改写后的语句 / 索引 DDL>
```

### 验证
- 改写前：<指标>
- 改写后：<指标>（需用户实测回填）

### 未验证
- <缺少实际计划或数据量时不能成立的判断>
```

**纪律**

- 没有实际执行计划时不宣称「这里一定慢」；只给待验证假设。
- 索引建议必须说明列顺序依据与写放大代价。
- 不改动生产库；DDL 只以文本给出，由用户执行。
